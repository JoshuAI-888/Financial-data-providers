From vendor scorecard to guided decision system

This tool selects an Investment Data Platform (IDP) for an institutional multi-asset manager whose strategic estate is Databricks. Its governing principle is buy investment-domain complexity; build differentiated investment intelligence. Rather than ask "which vendor scores best?", it works forward from strategy: what needs to change, how mature it must become, who should own it, and what to build or buy — then derives the vendor weighting from those answers and explains every score.

The four questions

  1. What needs to change? Strategically important, weak or painful capabilities.
  2. How good must it get? Target maturity and SLA — best-in-class is not automatically required.
  3. Who should own it? Internal · IDP · Databricks · specialist · managed · hybrid.
  4. Who can prove it? Evidence-capped vendor fit, hard gates, PoV, references, risk.

How to use it

Start in Strategy & Outcomes or pick a preset. Set current/target maturity and ownership; the Score & Evidence tab derives the weights and ranks the fifteen candidates live, each with a plain-language "Why this score?". Sensitivity shows whether the result is robust.

This is a Stage-1 paper screen — provisional, evidence-capped, not a selection of record. Confirm through RFI, references and PoV.

Sensitivity & robustness

Does the recommendation survive a change of mind? Each row re-runs the full model under one priority shift and shows the new top three. A leader that holds across scenarios is robust; one that flips is fragile.

Decision confidence & rank stability

A high numeric score is not the same as high confidence. Stability = how often a vendor stays top-3 across the tested scenarios.

Evaluation-process confidence

Proof-of-value test design

Every finalist completes the same test on the same data under the same rules — to stop any vendor controlling the evaluation with a polished canned demonstration. Provide ~500–1,000 instruments across equities, ETFs, govvies, credit, FX and private holdings, seeded with deliberately difficult conditions: duplicate securities, multiple listings, changed tickers, stale/outlier/missing prices, conflicting sources, bad identifiers, a corporate action, a historical correction, incomplete private data, an unfamiliar private-market PDF, and transaction/position records.

Test 1 · Instrument & entity mastering

Measure auto-match rate, false-match rate, unresolved rate, human touches per 1,000, elapsed time. False matches penalised harder than unresolved records.

Test 2 · Price validation

Baseline human review effort vs PoV effort. Target ≥ 80% reduction in manual price-validation effort without reducing agreed controls.

Test 3 · 07:00 portfolio SLA

Simulate an overnight cycle; measure feed completeness, outstanding exceptions, portfolio completeness, timeliness, operational visibility.

Test 4 · Databricks

Real mastered data becomes queryable in the evaluation Databricks: SQL, Python, Unity Catalog, schema, lineage, refresh, entitlements.

Test 5 · Unseen dataset

Introduce a previously unseen dataset mid-PoV; measure elapsed hours to ingested → mapped → validated → documented → governed → queryable.

Test 6 · Point-in-time

"What would a user have seen at timestamp X, before correction Y arrived?" — proof required from stored events/versions, not a destructive overwrite.

Test 7 · Private-equity document

Extract fund, company, commitment, capital call, distribution, NAV, valuation, currency, date from an unfamiliar GP document — each field linked to evidence.

Test 8 · Enterprise AI model

Using the organisation's chosen LLM: "What material portfolio exposures changed today, what caused them, and what source evidence supports the answer?" — vendor must not require its proprietary model.

Test 9 · User self-service

Representatives from PM, analysis, operations and quant complete defined tasks without vendor assistance.

Test 10 · Exit

Export raw + mastered data, historical versions, schemas, mappings, rules, exceptions, overrides, audit records, metadata. No realistic exit → major reversibility penalty.

Red flags to investigate

  • "Yes, we support that" without evidence.
  • IBOR based primarily on overnight snapshots.
  • Point-in-time achieved only by exporting to an external warehouse.
  • AI capability requiring the vendor's proprietary LLM.
  • AI roadmap presented as GA capability.
  • MCP server exposing only a small demonstration subset.
  • "Databricks integration" that is actually scheduled CSV export.
  • Lineage that stops at the vendor's ingestion boundary.
  • No separation of content licence and platform fee.
  • AUM pricing with steep nonlinear growth.
  • Every new dataset requires professional services.
  • Model extensions require vendor coding.
  • Inability to export configuration.
  • Contract gives the vendor rights over derived client data.
  • Manual exception work hidden inside "managed service".
  • Unresolved APAC support model.
  • Many acquired components with inconsistent data models.
  • Roadmap dependent on unreleased platform consolidation.
  • References far larger than this org, with huge implementation teams.
  • An implementation proposal that cannot define a 30–60 day PoV, or no meaningful answer on AI licensing rights.

Methodology & evidence standard

This v2 combines two disciplines. From the original evaluation it keeps evidence over claims, production over roadmap, hard gates before scoring, common proof-of-value tests, evidence caps, Databricks openness, AI model-independence, data-licensing rights, exit/reversibility, strategic-architecture penalties and five-year TCO. To that it adds a guided operating-model front-end drawn from established asset-management capability-maturity and target-operating-model practice: stakeholder intent → current state → capability maturity → strategic importance → sourcing strategy → target operating model → architecture → provider selection. Weights are a consequence of strategy, not an independent subjective input.

Weight-derivation formula

For each capability, priority = 0.30·importance + 0.20·urgency + 0.20·outcome-dependency + 0.15·current-pain + 0.15·target-maturity (all inputs normalised 0–1). IDP requirement strength = priority × ownership-relevance factor. Domain weight is the sum of requirement strengths in a domain, adjusted by architecture principles, normalised to 100%. Transformation urgency (from the maturity gap) is shown separately and does not feed vendor weight.

Score architecture — four separate numbers

Capability fit (0–100), evidence confidence (0–100), strategic-risk penalty (0–20) and commercial fit are kept distinct. Evidence never simply multiplies fit to zero; it acts as a requirement-level cap, a confidence measure and a gate — so a plausible platform with thin public disclosure is not punished as if it had failed.

Evidence caps

Roadmap 1.0 · sales assertion 2.0 · official documentation 3.0 · live demo 3.5 · named comparable customer 4.0 · contractual SLA 4.5 · organisation-specific PoV 5.0. Every material factual claim in a "Why this score?" panel carries a typed, dated citation, and vendor-authored evidence is badged distinctly from independent validation.

What must never happen
  • Hide the weighting logic or turn sliders into an opaque score.
  • Treat "unknown" as "bad", or let roadmap capability score as GA.
  • Let unneeded best-in-class capability inflate fit above the target.
  • Report a single composite number without its confidence.
  • Rank vendors without exposing the assumptions behind the ranking.
